# 実装レビュー：メモリ・GPUリソースと異常系

レビュー日: 2026-09-29  
対象: `3174b4e67cd704dad58e9b195397f9b2947819e2` を基点とする現在の作業ツリー。既存の未コミット変更 `src/app/App.svelte`、`src-tauri/tauri.conf.json` を含む。アプリ実装の修正は行っていない。

## 結論

**優先修正すべき重大な問題が2件ある。** 高解像度書き出し時の中間テクスチャ確保量がレイヤー数に比例して増え、384 MiBのキャッシュ予算ではピークも常駐量も制限できない。また、プロジェクト切り替えで不要になった画像のGPUテクスチャがキャッシュに残り続ける。いずれもGPUメモリ圧迫、コンテキスト喪失、描画・書き出し失敗につながり得る。

実GPUのOOMやドライバクラッシュを再現したという結論ではない。以下の容量は、実装が要求するテクスチャの画素容量を計数した値であり、ドライバの実使用量・解放完了時刻は測定していない。GCによる最終回収の可能性がある解放漏れと、Mapから到達可能なまま蓄積する問題も区別した。

| ID | 優先度 | 問題 | 検証 |
| --- | --- | --- | --- |
| R1 | P1 | 高解像度の全中間結果を確保してから予算整理する | 模擬GLで容量計数 |
| R2 | P1 | CPUアセットの削除がGPUキャッシュに伝わらない | 模擬GLで残存数確認 |
| R3 | P2 | サムネイル経由の低解像度キャッシュに掃除・予算処理がない | 模擬GLで容量計数 |

## R1 — 高解像度書き出しのGPUメモリ使用量が予算で制限されない [P1]

**位置:** `src/render/pipeline/MatcapPipeline.ts:86,98,148,162`、`src/render/export/Exporter.ts:143`、`src/app/dialogs/ExportDialog.svelte:25`。

`renderStack()` は各生成レイヤーの `layer:*` と合成途中の `acc:*` を固定解像度のターゲットに保持する。`evict()` は全レイヤーの処理後にしか動かず、削除対象も `layer:*` だけで、`acc:*` は残る。単発の書き出しにもこの差分描画用キャッシュを使用するため、大量の結果を同時保持する必要のない場面でもピークが増える。

RGBA16F・4096角では1枚128 MiB。グループ・マスク・フィルターなしの生成レイヤー10枚で、実装は空背景1枚＋生成10枚＋累積10枚＝**21枚、2,688 MiB**を要求する。整理後も空背景＋累積10枚＝**1,408 MiB**残る。模擬GL検証で両方の値を確認した。8192角では同じ構成のピークは10.5 GiB相当になる。

この値には画像アセット、常設のプレビュー用パイプライン、読み戻し用配列を含まない。Paddingはさらにフル解像度のRG32F×2、出力ターゲット、任意の平滑化ターゲットを使用する。`runFilter()` も全passの一時ターゲットを最後まで保持する。384 MiBは各パイプラインのソフト予算であり、アプリ全体の上限ではない。

**通常操作の再現:** 生成レイヤーを10枚用意し、4096で書き出す。書き出しダイアログの48px角プレビューも `crop` が読み戻し領域にしか効かず、同じフル解像度の生成・Paddingを行うため、サイズを選ぶだけでこの確保経路に入る。実機での大容量試験は慎重に行うこと。

**修正方針:** 単発書き出しには前段の累積結果と現在の入力だけを保持する経路を設ける。グループ・レイヤーマスクの参照寿命を考慮し、不要になった結果を順次再利用する。プレビューにも確保前の総量制限を設け、低解像度化などに切り替える。Padding用seed・filter中間結果も最終使用直後に解放・再利用する。

**回帰確認:** 4K/8K、10/50レイヤー、多段filter、グループ、マスクでピークを計数する。予算超過を確保前に扱い、書き出し完了・失敗後に所有するターゲットが残らないことを確認する。

## R2 — プロジェクト切り替え後も不要な画像テクスチャが残る [P1]

**位置:** `src/app/actions.ts:107`、`src/core/io/assetStore.ts:125`、`src/render/pipeline/resources.ts:33,115,147`。

`setDocument()` は `assets.retain()` で不要なCPUエントリーとbitmapを削除する。一方、`ResourceCache.assets` に格納したテクスチャを消す `dropAsset()` はアプリから呼ばれていない。`retain()` も削除通知を発行しない。新規ドキュメントでもRendererは同じなので、一度アップロードした異なる画像がセッション中のMapに残り続ける。

**再現:** 画像を含むプロジェクトAを表示→新規作成→別画像のプロジェクトBを表示、を繰り返す。模擬GLで画像追加・アップロード・CPU側clearを5回行うと、CPUアセット0件に対してGPUテクスチャは5件残った。4096角RGBA8画像はミップマップを含め約85.3 MiBなので、異なる画像の蓄積は大きい。通常終了・コンテキスト喪失まで待つ運用では長時間利用を保護できない。

**修正方針:** AssetStoreの削除をResourceCacheに通知し、そのIDのテクスチャを削除するか、ドキュメント切り替え時に有効ID集合でGPUキャッシュを整理する。CPU/GPU両方の寿命を対応づける。

**回帰確認:** A→新規→B→新規を繰り返し、GPUアセット数・推定bytesが毎回基準値に戻ることを検証する。

## R3 — サムネイルだけで使用する低解像度パイプラインが増え続ける [P2]

**位置:** `src/render/Renderer.ts:120,207`、`src/render/pipeline/MatcapPipeline.ts:104`、`src/app/viewport/thumbnails.ts:34`。

通常フレームは `hi.render()`、サムネイルは `lo.layerOutput()` を使う。後者は `generate()` で512角のslotを追加するだけで、`render()` にある生存レイヤーの確認・不要slot削除・`evict()` を実行しない。スライダードラッグ等で `interactive=true` のフレームが来るまで、削除したレイヤーや以前のドキュメントのslotが低解像度側に残る。

**再現:** スライダーを操作せず、生成レイヤーの追加・サムネイル生成・削除を繰り返す。またはレイヤーIDの異なるプロジェクトを順次開く。模擬GLで異なる200レイヤーに `layerOutput()` を呼ぶと、背景を含め**402 MiB**を保持し、384 MiBを超えても整理されない。実際の追加・削除イベントとサムネイル取得間隔はこの再現の前提。

**修正方針:** サムネイル側にも現行ドキュメントの生存IDと予算を適用する。64pxサムネイルのために512px出力を無期限保持しない設計も検討する。

## R4 — 不要なCPU画像・ファイルをUndo履歴から消えた後も保持する [P2]

**位置:** `src/app/actions.ts:364,430`、`src/core/io/assetStore.ts:74,125`、`src/core/commands/store.ts:148`。

画像・メッシュの取り込みはグローバルAssetStoreに元ファイルbytesと、画像ならデコード済みbitmapを格納する。レイヤー削除、画像・ノーマルマップの差し替え、履歴の上限300件による破棄ではアセット回収が走らず、`retain()` のアプリ内呼び出しはドキュメント切り替え時だけである。Undoのための一時保持は必要だが、Undo/Redoから到達不能になったアセットまで同一ドキュメント中ずっと保持する理由にはならない。

**再現:** 異なる大きな画像の取り込み・削除を繰り返し、履歴上限を超える。現在のレイヤーが少なくても `assets.ids()` とデコード画像容量は減らない。4096角RGBA8相当のデコード画像だけで1件64 MiB相当、これに元ファイルbytesとR2のGPU分が加わる。

**修正方針:** 現在のドキュメント・view・Undo/Redo履歴から参照されるIDの和集合を管理し、履歴破棄時にも回収する。現在のレイヤーだけを見て削除するとUndoが壊れるため、そこは別途考慮する。

## R5 — 同一IDのrestoreで旧ImageBitmapをcloseしない [P2]

**位置:** `src/core/io/assetStore.ts:102`、`src/app/actions.ts:190`、`src/app/presets/user.ts:31`。

`restore()` は既存IDでも新しいentryを作成・decodeし、`entries.set()` で上書きする。`decode()` 内の `entry.bitmap?.close()` は新規entryに対する処理なので、以前のentryのbitmapは閉じない。同じプロジェクトの再読み込みや同じ画像を含むプリセットの反復適用で発生する。

模擬bitmapで同じIDを2回restoreしてからclearすると、2枚目のcloseは1回呼ばれるが、1枚目は0回だった。**旧bitmapのJS参照は失われるので、永続的な到達可能オブジェクトのリークと断定はしない。** 明示解放が抜け、ネイティブ画像の回収時期をGCに依存させる不具合である。

**修正方針:** 内容が同一なら既存entryを再利用する。差し替えるなら新画像のdecode成功後に旧bitmapをcloseして置換する。バージョン番号も単調に更新しGPUキャッシュ更新と整合させる。

## R6 — Paddingターゲットの確保途中の失敗でdelete漏れ [P2]

**位置:** `src/render/export/Exporter.ts:206`。

`a`、`b` を順に作った後で `own.push(a, b)` する。`b` のFramebuffer作成が失敗すると、`a` は外側finallyが処理する所有リストに入らない。実装上、`b` 自身とpipelineは解放されるが、`a` のtexture/FBOは明示削除されない。

模擬GLで空背景→seed a→seed bの3番目のFramebuffer検査を失敗させ、書き出し終了後に1枚のターゲットが残ることを確認した。4KのRG32Fなら128 MiB相当の解放漏れとなる。こちらも最終的なブラウザー側GC回収はあり得るが、メモリ不足時に明示解放を逃す点が問題。

**修正方針:** 1枚の確保が成功するたびに即座に所有リストへ追加する。filterの一時ターゲットにも例外時の返却を設ける。

## R7 — Rendererの終了・コンポーネント破棄で全リソースを解放できない [P3]

**位置:** `src/app/viewport/Viewport.svelte:101`、`src/render/Renderer.ts:251`、`src/render/preview/MeshPreview.ts:33`、`src/render/gl/gl.ts:40`。

Viewportのcleanupはイベント購読とRAFを解除するが、`renderer.dispose()` を呼ばない。さらにdisposeを呼んでも、defaultNormal、MeshPreviewのVBO/IBO/VAO・program・MSAA color/depth/FBO、GLContextの空VAOは処理対象にない。canvasのcontextイベントは匿名関数で登録され、解除されない。settleタイマーと保留中サムネイルのキャンセルもない。

現在のAppは通常Viewportを1個維持するため、日常操作だけでRendererが何度も作られるという指摘ではない。再マウント、HMR、将来の複数ビューなどで決定的な解放を保証できない。メッシュを球プレビューへ切り替えた際の保持は再利用目的とも考えられるが、最終disposeで残るのは別問題。

**修正方針:** 所有クラスごとに完全なdisposeを設け、Viewportから呼び出す。イベント・タイマー・idle処理も解除し、破棄後の再描画を抑止する。

## R8 — シェーダーコンパイル失敗時の頂点シェーダーdelete漏れ [P3]

**位置:** `src/render/gl/gl.ts:103`。

頂点シェーダーのcompile成功後、フラグメントcompileがthrowすると、後続の `deleteShader(vs)` に到達しない。失敗したフラグメント自体はcompile内でdeleteされる。失敗注入で頂点シェーダー1個にdeleteが呼ばれないことを確認した。

ResourceCacheは同じLayerDefの失敗を記録するため、毎フレーム増殖するわけではない。不正なプラグインの再読み込みなどが発火条件で、テクスチャ問題より影響は小さい。

**修正方針:** shader/programの生成からlinkまでをtry/finallyで囲み、成功済みのハンドルを各失敗段階で解放する。

## R9 — 不正バージョン番号で同期ループが終了しない [P2]

**位置:** `src/core/io/serialize.ts:150,210`。

`typeVersion` と `schemaVersion` は有限数かどうかだけを確認し、下限・整数・安全整数の制約がない。負の大きな値だとmigrationのwhileを膨大な回数実行する。例えば `-1e20` はJavaScriptの精度により `+1` しても同じ値のため、`ver++` / `tv++` が進まず永久ループになる。小さなJSONでもプロジェクト読み込みでメインスレッドを停止できる。

**再現入力:** 通常の保存JSONの `schemaVersion` だけを `-1e20` に変更する。または対応済みレイヤーの `typeVersion` を同値にする。実アプリを止める入力実行は行っていないが、ループ条件と数値演算から判定できる。

**修正方針:** バージョン番号を正の安全整数に制限する。不正値を拒否または定義済み初期値に変換し、移行回数をサポートするバージョン数で制限する。

## R10 — ZIP展開と画像decodeに入力規模の上限がない [P2]

**位置:** `src-tauri/src/commands/project.rs:84`、`src/platform/web.ts:106`、`src/core/io/assetStore.ts:109`。

Rust側はZIP内のproject.jsonと全assetsを `read_to_string` / `read_to_end` で上限なくRAMへ展開し、その後IPC用にpackする。Web側も `unzipSync()` で全entryを同期展開する。画像は画素数の制限なくdecodeし、GPUアップロードにもMAX_TEXTURE_SIZEを使った画像寸法チェックがない。

通常のファイルで必ず問題になるという指摘ではない。圧縮率の高い大規模ZIP、意図せず巨大な画像を含むプロジェクトで、エラーとして回復する前にメモリを使い切ったりUIが長時間止まる経路がある。ZIPパストラバーサルの検査やテストは存在するが、展開容量の保護とは別である。

**修正方針:** entry数、各entryと総展開量、project.jsonサイズ、画像画素数を制限する。ZIPの宣言サイズだけでなく実読み取り量も制限し、Web版ではworker/非同期処理でキャンセル可能にする。CPU decodeの上限とGPU寸法上限を別々に検証する。

## 修正と再計測の順序

1. R1の単発書き出し経路とR2のCPU/GPU削除連携を優先する。
2. R3・R4を修正し、プロジェクト切り替えと追加・削除を繰り返して容量が一定範囲に戻ることを確認する。
3. R5〜R8の生成途中・失敗・終了処理を統一し、各確保段階への失敗注入を回帰テストにする。
4. R9・R10の入力制限を追加する。
5. 実GPUで確保ピークと回復を計測する。現状の `Renderer.memoryBytes` はプール、画像キャッシュ、noise、meshのMSAA/VBO等を含まないため、総VRAM表示として扱わず、計測対象を拡張する。

## 対応状況（2026-09-29）

| ID | 対応 |
| --- | --- |
| R1 | 書き出し用に差分キャッシュを使わない `MatcapPipeline.renderOnce()` を追加。各段で「下の合成結果・入力・出力」だけを保持し、残りはすぐプールへ返す（4K・生成10枚でピーク 2,688 MiB → 384 MiB、処理後は結果1枚だけ）。空の背景は 1×1 の透明ターゲットにした。filter の中間結果は次の pass が読んだ直後に返却し、Padding の seed 2枚は resolve 直後に解放。`estimateExportBytes()` で確保前に総量を見積もり、上限（3 GiB）を超える書き出しは確保前にエラーにする。書き出しダイアログのプレビューは見積もりが 256 MiB を超えると解像度を下げ（Padding も比例）、その旨を表示する。`RenderTarget` は確保直後に `OUT_OF_MEMORY` を検出して解放・エラーにする |
| R2 | `AssetStore.onRemove()` を追加し、`retain()` で消したIDを通知。`ResourceCache` が購読してGPUテクスチャを削除する。CPU側にないIDのテクスチャも参照時に削除 |
| R3 | サムネイル生成時に現行ドキュメントの生存IDを渡し、消えたレイヤーのslotを解放。`layerOutput()` でも予算による整理を行う |
| R4 | 履歴変更の2秒後に、ドキュメント・ビュー・Undo/Redo履歴（パッチ内の文字列）から到達できるID以外を回収。取り込み直後（10秒以内）のアセットは残す |
| R5 | 同じIDで同じ内容の `restore()` は既存entryを再利用。内容が違う場合は新しい画像のdecode後に旧bitmapをcloseし、versionを単調に増やす |
| R6 | Paddingのターゲットを1枚ずつ所有リストへ追加。filterの一時ターゲットも例外時に返却 |
| R7 | Viewportの破棄で `renderer.dispose()`、settleタイマー、保留中サムネイルを解除。disposeはdefaultNormal、MeshPreview（VBO/IBO/VAO/program/MSAA FBO）、空VAO、contextイベントまで解放し、以後の描画を止める。`Renderer.memoryBytes` に画像・noise・meshの推定量も含めた |
| R8 | `Program` の生成〜linkを try/finally で囲み、各段階で作成済みのハンドルを解放 |
