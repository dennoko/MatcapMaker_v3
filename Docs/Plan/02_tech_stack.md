# 02. 技術選定

## 1. 評価軸

1. **UX の作り込みやすさ**：ギズモ、グラデーションエディタ、カーブエディタ、ドラッグ＆ドロップ、アニメーションなど独自 UI の実装コスト
2. **軽さ**：配布サイズ、起動時間、メモリ
3. **GPU 描画の堅牢さ**：Windows のさまざまなドライバ（特に Intel 内蔵 GPU）で安定して動くか
4. **ビルドと配布**：コマンド 1 つで単体 exe を作れるか。署名なしで配布したときの誤検知の起きにくさ
5. **拡張性**：レイヤーの追加、将来のプラグイン、Web 版の可能性

## 2. 候補の比較

| 候補 | UX の作り込み | 軽さ | GPU の堅牢さ | ビルド/配布 | 拡張性 | 総評 |
|---|---|---|---|---|---|---|
| **A. Tauri 2 + Svelte + WebGL2** | ◎ Web の UI 資産をそのまま使える | ○ exe 約 10MB、RAM は中程度 | ◎ ANGLE 経由で D3D11 | ◎ `tauri build` 一発で exe | ◎ Web 版も同じコードで動く | **採用** |
| B. Rust + egui + wgpu | △ 即時モード UI で見た目の作り込みに手間がかかる。日本語 IME がやや弱い | ◎ exe 約 10MB、RAM 最小 | ◎ D3D12/Vulkan | ◎ `cargo build` 一発 | ○ | 次点。最軽量を優先するならこちら |
| C. C++ + Dear ImGui + OpenGL | △ | ◎ | △ OpenGL ドライバに依存 | △ CMake と依存管理 | △ | 開発効率が低い |
| D. Electron + WebGL2 | ◎ | ✕ 100MB 超 | ◎ | ○ | ◎ | 重さの目標を満たせない |
| E. Python + PySide6（現行の改良） | ○ | ✕ 200MB 超、起動が遅い | △ OpenGL | △ PyInstaller は誤検知されやすい | ○ | リメイクする意味が薄い |
| F. Qt 6 (C++) + QML | ○ | ○ 30〜50MB | ○ RHI | △ Qt の配布とライセンス（LGPL）の管理 | ○ | ビルド環境が重い |

## 3. 採用構成の詳細

```
┌──────────────────────────── MatcapMaker.exe (Tauri 2) ────────────────────────────┐
│  WebView2 (Chromium)                                                              │
│  ┌────────────── Frontend (TypeScript) ──────────────┐                            │
│  │ UI: Svelte 5 components                            │                            │
│  │ Core: model / commands / layer defs / i18n  ← UI 非依存の純 TS                  │
│  │ Render: WebGL2 renderer (RGBA16F, GLSL ES 3.0)     │                            │
│  └───────────────────────▲───────────────────────────┘                            │
│                          │ Tauri IPC（JSON と生バイナリ）                            │
│  ┌───────────────────────┴──── Backend (Rust) ───────┐                            │
│  │ ファイルダイアログ / プロジェクト (zip) 入出力 / PNG・EXR エンコード                │
│  │ 設定 / 自動保存 / クラッシュログ / 単一インスタンス                                │
│  └────────────────────────────────────────────────────┘                            │
└───────────────────────────────────────────────────────────────────────────────────┘
```

### 3.1 Tauri 2（アプリシェル）
- OS 標準の **WebView2** を使うので、ブラウザエンジンを同梱しません。release ビルドの exe は **単体で約 5〜12MB** に収まり、フロントエンドの資材は exe に埋め込まれます。
- WebView2 は Windows 11 に標準搭載、Windows 10 にも Edge の更新で事実上入っています。入っていない環境向けには NSIS インストーラに bootstrapper を組み込めます（06 参照）。
- 公式プラグインが揃っています：`dialog`, `fs`, `store`（設定）, `single-instance`, `window-state`, `updater`（任意）。
- 生バイナリの IPC（`tauri::ipc::Request` / `Response`）を使えば、4K RGBA16F（128MB）の読み戻しデータも JSON 化せずに Rust へ渡せます。

### 3.2 Svelte 5 + TypeScript + Vite（UI）
- コンパイル型でランタイムが小さく、runes による細かい単位のリアクティビティのおかげで、スライダーを 1 本動かしても再描画は該当部分だけで済みます。
- 選択肢としては SolidJS も同等です。React はランタイムと再レンダリングのコストの面で外しました。
- UI 部品は自作を基本とします（スクラブ式数値入力、カラーピッカー、グラデーション/カーブエディタ、ギズモ）。ヘッドレス UI（Bits UI など）は、ダイアログやメニューなどアクセシビリティが重要な部品に限って使います。
- スタイルは CSS 変数で組んだデザイントークンで管理し、ダーク/ライトのテーマを持たせます。

### 3.3 WebGL2（描画）
- **Windows 上の WebGL2 は ANGLE によって Direct3D 11 で動きます**。現行が抱えている「ベンダーごとの OpenGL ドライバの品質差」を避けられます。
- `EXT_color_buffer_float` で RGBA16F の FBO に描けるので、内部を HDR にするのは最初から可能です（16F は WebGL2 の標準機能でリニアフィルタもかかります）。
- three.js などの 3D エンジンは使いません。必要なのは「フルスクリーン quad のパス」と「メッシュ 1 つへのプレビュー描画」だけなので、数百行規模の薄いラッパーで足ります。バンドルが小さく、GL の状態もすべて自分で管理できます。
- **WebGPU への移行経路**：レンダラーを `RenderBackend` インターフェースの背後に置き、シェーダーはレイヤー定義側で「関数本体」として持たせます。将来 WGSL 版を併記すれば差し替えられます。WebView2 はすでに WebGPU に対応していますが、ドライバのブロックリストが広い点を考え、既定は WebGL2 とします。

### 3.4 Rust（バックエンド）
| 役割 | クレート |
|---|---|
| PNG（8/16bit、straight alpha）エンコード | `png`（`image` の一部） |
| EXR（16F）エンコード | `exr` |
| プロジェクトの zip 入出力 | `zip` |
| シリアライズ | `serde`, `serde_json` |
| ログ | `tracing` + ファイル出力 |

- **PNG のエンコードを Rust で行う理由**：Canvas 2D の `toBlob` は内部で乗算済みアルファに変換するため、半透明部分の色が劣化します。パディングで外に広げた色の精度を保つには、生のピクセルを受け取って自分でエンコードする必要があります。
- 重い画像処理（パディング）は GPU 側で行います（04 参照）。Rust はエンコードとファイル I/O だけに専念させ、責務をはっきり分けます。

## 4. 次点案（B：egui + wgpu）を選ばなかった理由
- 最軽量（RAM 数十 MB）で、ビルドも `cargo build` 一発と魅力的です。
- ただし本アプリの価値は「直感的な操作感」にあり、グラデーション/カーブエディタ、ギズモ、サムネイル付きのドラッグ＆ドロップリスト、アニメーションなどを作り込むコストは Web 技術のほうが明らかに低いと判断しました。
- 日本語 IME の入力（レイヤー名など）や、フォント描画の質も Web 側が有利です。
- **判断を見直す条件**：Phase 0 のスパイク（07 参照）で WebView2 のメモリや起動時間が目標を大きく超えた場合は、B に切り替えます。コアのロジック（レイヤー定義、GLSL、プロジェクト形式）は移植できる形で設計しておきます。

## 5. 開発環境
- Node.js LTS + pnpm、Rust stable（MSVC toolchain）、Visual Studio Build Tools（C++ ワークロード）
- エディタ：VS Code + rust-analyzer + Svelte 拡張
- テスト：Vitest（コア）、Playwright（UI の E2E とシェーダーのゴールデン画像）、`cargo test`（Rust）
